# 專題討論與決策紀錄

記錄從題目選定到期中報告後的主要討論與決定，方便組員和之後的自己回頭查原因。

## 1. 起點（2026-11-11）

- **題目來源**：信義公益基金會「集點子」平台的〈長輩專屬拜拜路線推薦〉。原構想是語音或大按鈕介面、依長輩狀況推薦少樓梯有座椅的路線、整合公車與廟宇活動、語音導航與平安回報。
- **課程要求**：11/12 期中簡報約 10 分鐘，須包含四項：Problem Introduction、Potential Methods/Models/Algorithms、Team Responsibilities、Connection to the USR Competition。
- **成績比重**：Innovation Ideas 10% 與 Final Project 20% 都和 USR 競賽相關。
- **形式決定**：PPTX 簡報加講稿、全英文、期末做可操作的原型、五人分工先以 Member A–E 代稱。

## 2. 範圍如何收斂

| 版本 | 方向 | 結果與原因 |
|---|---|---|
| v1 | 語音辨識、意圖理解、地圖、語音合成全部串現成 API | 退回：技術幾乎都是串接，和多媒體課程的連結太弱 |
| v2 | 音訊（降噪、聽力補償）＋影像（樓梯偵測、低視力增強）＋向量圖（Bézier 簡化地圖）全部自己實作 | 退回：一兩個月做不完；而且拜拜情境其實不需要影像處理，廟宇照片只是給人參考 |
| v3（定案） | 只做**聲音的輸入前處理與輸出處理**，語音辨識與合成用現成 API | 規模約一個月、負擔合理；技術主體對應課程 Unit 4 數位音訊 |

v3 的內容：

- **輸入前處理**：轉成 16 kHz、16-bit、單聲道 → 以短時能量（dB）做語音偵測 → Hamming 窗＋FFT 的頻譜相減降噪 → 音量正規化。
- **輸出處理**：在頻域加強約 1–4 kHz 的聽力補償 EQ、響度正規化；語速放慢只是 API 參數。
- **路線推薦**：關鍵字擷取意圖（語言模型備案），開放資料＋OpenStreetMap，限民雄、新港，人工補標樓梯與座椅。
- **評估**：實地錄 20–30 句指令，同一個語音辨識 API 比較「原始」和「前處理後」的字元錯誤率（CER），另做處理前後的波形與頻譜圖、長輩聽感問卷。

### 為什麼取樣率定 16 kHz

依 Nyquist 定理，16 kHz 可表示到 8 kHz，涵蓋語音辨識需要的母音共振峰與子音高頻成分。8 kHz（電話）只到 4 kHz，會丟掉子音細節；44.1 kHz（CD）多出的頻段對辨識沒幫助，只增加資料量。多數語音辨識服務也以 16 kHz 為建議輸入。手機錄音若是 44.1/48 kHz，降取樣前要先低通濾波避免混疊。實際取樣率仍要以選定 API 的文件為準。

### 聽力補償 EQ 曲線

簡報上的曲線（1 kHz 以下約 0 dB、2–4 kHz 拉到 6–8 dB、4 kHz 以上降回 3–5 dB）是**示意的起始設定，不是量測或文獻數據**。「老年性聽損以高頻為主、加強子音頻段」這個方向有依據，具體數字要靠長輩試聽調整，或之後查老年性聽損的平均聽力圖再修正。

## 3. 簡報修正（依組內註解）

- **第 2 頁**：原本左邊講長輩不出門的原因、右邊講語音辨識的缺點，中間缺了「為什麼用語音」，改成「不出門的原因 → 我們的想法：用語音問路 → 但語音在戶外會失靈」三段。
- **投影片上不標課程單元**：報告內容用到課程知識即可，不需要在投影片上寫出是哪一單元；課程標籤全部拿掉，講稿裡保留一兩句口頭帶過。
- **字級放大**：各頁小標題與說明文字放大到報告現場看得清楚的大小。
- **第 4 頁**：上排加框標「User flow」（使用者使用流程），下排加框標「System pipeline」。
- **評估獨立一頁**：原本和路線權重放在同一頁，但兩者主題無關，拆成兩頁。
- **介面定位修正**：不是「不能打字、沒有選單」，而是語音按鈕為主、打字與選單為輔；保留後者是為了之後擴充新功能。說完話後整條 pipeline 自動執行，語音指引為主、螢幕路線為輔。
- **新增第 5 頁**：嵌入介面示意動畫。

## 4. 介面示意

- `BaiBaiGo_mockup.html`：純前端、可點擊的手機畫面，流程為首頁 → 聆聽 → 自動處理 → 推薦 → 導航 → 抵達與平安回報。導航畫面以地圖為背景，顯示目前位置與路線，上方疊轉彎指引卡與語音指引條。
- 地圖是手繪的向量示意，不是真實街道；廟宇名稱、距離、樓梯與座椅數量都是示範資料。
- `assets/baibaigo_demo.gif`：把示意介面逐格截圖合成的循環動畫（27 格、約 22 秒）。

## 5. 作品名稱

建議報名名稱：**拜拜 Go：聽得懂長輩的拜拜路線夥伴**（英文：BaiBai Go: A Voice-First Temple Route Companion for Seniors）。

- 主標與簡報、介面一致；副標點出「讓語音聽得懂長輩」這個技術重點；「夥伴」比「系統」更貼近競賽的長者幸福主題。
- 其他備選：「拜拜 Go：長輩專屬語音拜拜導航」、「說一聲，去拜拜：長輩語音路線夥伴」、「聲聲平安：長輩語音拜拜路線推薦」。
- 報名前要確認名稱字數規定，以及是否須標示原點子出處。

## 6. 期中後助教回饋（2026-11-12 之後）

助教認為這是以走路為主的 App，提出兩點建議，組內同意採納：

1. **把坡度算進去**：大斜坡會讓推薦不準。做法是評分加一項坡度，沿路線取海拔算坡度，只罰上坡、超過門檻才重罰，權重隨行動狀況調整；短陡坡靠實地踏查補標。
2. **走太遠時推薦大眾運輸**：步行超過上限時改推薦「走到站牌 → 搭公車 → 走到廟」，用 TDX 或地圖服務的現成大眾運輸資料，不自己做轉乘演算法。
